# 多场训练赛后的协作与终稿经验

本文件记录在多次完整训练赛中反复出现、且已经验证过的仓库操作与论文终稿经验。它不是新的论文模板，而是对 `README.md`、`PAPER_STYLE_GUIDE.md` 和 `FINAL_PAPER_CHECKLIST.md` 的工程补充。

## 1. 临时 chore 分支是一次性的

`feature/*` 是长期责任分支；`chore/*` 只用于一次集中维护、迁移、模板升级或批量修复。

若 `chore/*` 通过 **squash merge** 进入 `main`，Git 历史会表现为：

```text
main        多出 1 个压缩后的综合提交
chore/*     仍保留原来的若干细粒度提交
```

此时比较 `main...chore/*` 往往会显示双方都 ahead/behind，属于正常的历史分叉，不代表还应该把 chore 再 merge 一次。正确做法是：

1. 用 `git diff` / GitHub compare 核对综合提交是否已经覆盖需要保留的内容；
2. 确认后删除旧 `chore/*`；
3. 下一轮维护从最新 `main` 新建一个新的 chore 分支。

辅助检查：

```bash
python scripts/branch_hygiene.py
```

不要把已经 squash 过的旧 chore 分支继续当成“待合并半成品”。

## 2. 日常全文预览只做责任域 overlay

长期章节分支并行时，日常 preview 不再把所有 feature 分支临时 merge 到一起。经过多次比赛验证，稳定方式是：

```text
feature/paper-shell 作为全文排版底座
→ 审计每个责任分支是否越界
→ 只覆盖该责任域的 canonical 文件
→ 静态检查
→ 编译临时 PDF
```

一键入口：

```bash
git fetch origin --prune
bash <(git show origin/feature/shared:scripts/preview_latest.sh)
```

失败后先看**第一处硬错误**。XeLaTeX 第一遍出现 citation/reference warning 不等于最终引用失败；如果中途被缺图、TeX 拼写或冲突标记打断，后续轮次本来就没有机会解析引用。

## 3. 预览目录必须可自愈

失败的临时 worktree 经常会阻塞下一次 preview。预览脚本应只自动删除带模板 marker 的临时目录，不删除普通工作区。

`preview_latest.sh` 会主动清理 controller 和 preview worktree；`preview_merge.py` 也应在发现自己创建的旧 marker 目录时自动回收。

## 4. 每个论文模块只保留一个 canonical 正文源

出现过的高风险模式包括：

```text
references.tex
references_final15.tex
q2_final.tex
q2_v3.tex
真的final.tex
```

这些文件很容易造成“改了但 preview 没变化”，因为总装脚本可能仍读取另一份文件。

规则：

- 参考文献唯一正文源：`modules/70_references/paper/references.tex`；
- 每问唯一正文源：`modules/<q>/paper/q?.tex`；
- 伪代码可以拆成明确的 `q?_algorithm.tex`；
- 旧稿进入 `work/archive/`，不留在 `paper/` 目录；
- 不使用 `_final`、`_v2`、`_old`、`_backup` 等平行正文文件。

## 5. 静态检查要在 LaTeX 之前发现低级错误

多场比赛中真实出现过：

- `figures/` 与 `figure/` 路径写错；
- `\beginingroup` 拼写错误；
- `\\begin{table}` 多写一个反斜杠；
- Git 冲突标记残留在正文；
- `\lstinputlisting` 引用了 fast preview 没带入的代码；
- 图表存在但正文没有引用；
- `references.tex` 与正文 cite key 不一致。

因此 `final_preflight.py` 应尽量在 XeLaTeX 前检查：冲突标记、可解析资源路径、孤立图表、可疑 TeX 拼写、重复正文源和结果状态。

## 6. 正文结构优先于“文字写满”

问题描述、预备工作和算法介绍最容易出现连续五六行以上的散文块。推荐结构：

```text
对象/任务
→ 数据发现或关键困难
→ 数学量/定义
→ 建模作用
```

能用公式表达的定义不要写成长句；能由图表承担的比较不要在正文重复一遍。正文中的每张图表必须被引用并说明它回答了什么问题。

## 7. 正式写作不要带入讨论过程语言

终稿应直接写数学事实。需要重点清理的内部表达包括：

```text
物理口径
统计口径
证据边界
统一链路
层级结构
柔性释放/替代
严格 Cost 区间
严格闭合
基础的量化参考
```

需要说明范围时直接写具体时间、空间或样本范围；需要说明可行性时写“所有约束满足”；未证明全局最优时写“当前整数解未获得全局最优证书”。

模型或算法第一次出现使用：

```text
中文名称（English Full Name，缩写）
```

附件字段名和公认缩写可以保留；正文主动命名的对象不要无原因在中文、英文全称和缩写之间跳换。

## 8. 算法介绍至少给一个核心数学规则

算法小节不能只有一段自然语言和一张伪代码。至少给出决定算法行为的数学量，例如：

- 任务扫描排序键；
- 候选接受准则；
- 约化成本；
- Benders 最优性割；
- 收敛门限；
- 字典序固定约束。

然后再给伪代码。伪代码保留正式循环、判断和停止条件，动作描述以中文为主。

## 9. 多目标和场景结果必须区分“指标”与“证书”

不要用一个主观综合权重把全部题面指标揉成单一分数，除非题目明确要求。

对于大规模整数优化和场景分析，应明确区分：

- 已认证/已闭合结果；
- 与基准等价的退化场景；
- 只有上下界的有界结果；
- 通过硬约束检查的可行候选。

有界候选的等待、迁移、碳排等数值只能表述为“候选方案指标”，不能写成该场景的最优策略。

## 10. 跨问题比较前先统一计算范围

若不同问题的时间范围、终端结算、储能终端状态或购售电定义不同，不要直接把绝对成本差解释为某种“联合优化收益”。

跨问比较前至少核对：

```text
时间范围
终端小时是否计费
SOC 初末约束
新能源售电定义
成本/碳排单位
任务完成边界
```

若尚未统一，只比较同一问题内部的相对变化，或明确说明暂不解释跨问绝对差。

## 11. 代码与论文参数必须同源

正文中的蒙特卡洛次数、容差、迭代次数、时间范围和场景参数应与正式代码一致。终稿前抽查“代码常量 ↔ 正文数字”，不要为了迁就旧文案去改已验证程序。

结果进入正文前仍以 `results/registry.csv` 中当前项目的 `FROZEN + CHECKED` 为准。

## 12. 图表排版的稳定经验

默认视觉尺寸：

- 单小图：`0.44\textwidth`；
- 两个独立小图并排：每个约 `0.44\textwidth`；
- 已合成双面板：整张 `0.88\textwidth`；
- 总体流程图：`1.0\textwidth`；
- 机理图：通常 `0.70\textwidth`；
- 问题背景示意图：通常约 `0.60\textwidth`。

表格过窄时先局部增加 `\tabcolsep`；不要为了拉宽一个双列表而把所有表改成 `tabular*`，否则彩色表头可能出现不连续。

`[H]` 流程图后如果紧跟多行 `align`，出现页底大空白时先拆公式块，而不是先缩小流程图。

## 13. 摘要、参考文献和代码附录

- 摘要只加粗核心模型、核心算法和关键结论；
- 场景分析在摘要中直接回答“什么因素影响什么指标”；
- 15 条左右参考文献优先用 `\footnotesize` 和小条目间距争取一页；
- 若只交 PDF 且代码页不计正文页数，附录用 `\lstinputlisting` 收入各问最终实际运行的核心程序；
- 若另交源码，PDF 附录只列文件、功能和必要核心片段。

## 14. 一轮终稿检查顺序

推荐固定成：

```text
标题/摘要
→ 问题描述和预备工作
→ 模型汇总
→ 算法核心数学量与伪代码
→ 每张图表的引用和解释
→ 数值与代码一致性
→ 场景最优性表述
→ 参考文献
→ 代码附录
→ AI 使用报告
→ preview + final_preflight
```

这比只从第一页顺读到最后一页更容易发现结构性问题。
