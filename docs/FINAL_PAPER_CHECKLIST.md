# CUMCM 终稿写作与集成检查表

本文件记录最近几次完整训练赛中实际暴露的问题。它不是新的论文结构，而是对 `PAPER_STYLE_GUIDE.md` 的终稿检查补充；仓库操作层经验另见 `WORKFLOW_LESSONS.md`。

## 1. 正文不要出现大段连续叙述

“描述与分析”“预备工作”“模型求解”最容易写成连续五六行甚至更长的文字块。终稿优先采用：

1. 两到三个带含义的小分点；
2. 一条承担定义或判断作用的公式；
3. 图表 + 一到两句解释；
4. 必要时拆成两个自然段。

经验规则：一个纯文字段落若在当前版式中接近 5 行以上，应主动检查能否分点、分段或公式化。不要为了形式硬塞公式，但也不要把本可数学表达的内容全部写成散文。

问题描述建议直接按“任务对象 → 关键矛盾 → 建模选择”组织；预备工作按“数据发现 → 数学量 → 对后续模型的作用”组织。

## 2. 清理内部表达和 AI 式措辞

正式论文直接陈述对象、模型、公式和结果，不把团队内部讨论过程写进正文。

尽量避免把下列表达当成写作习惯：

- “本文为了……”“本文只保留……”反复自我说明；
- “物理口径”“统计口径”“证据边界”“层级结构”“统一链路”等内部术语；
- “严格 Cost 区间”“严格闭合”等没有必要的修饰词；
- “基础的量化参考”“机制链”“柔性释放/替代”等只在内部讨论中有意义的词；
- “不是……而是……”连续使用形成答辩式语气。

需要说明统计范围时，直接写“成本统计范围为 0--2405 h”；需要说明可行性时，直接写“所有约束均满足”；需要说明最优性不足时，直接写“当前整数解未获得全局最优证书”。

“本文”不是禁词，但不作为每段固定开头。优先写“建立……模型”“定义……”“结果表明……”。

## 3. 中文、英文和缩写统一

附件原字段名可以保留，如 `TaskType`、`LatestFinish`；正文主动命名的模型、算法和指标不要突然切换成英文。

模型或算法第一次出现统一写为：

```text
中文名称（English Full Name，ABBR）
```

例如：

```text
标记复合 Poisson（Marked Compound Poisson，MCP）模型
```

后文可直接使用中文简称或缩写。不要写成“Marked Compound Poisson workload model”后再另起中文名。

任务类型若附件使用英文枚举，首次出现时给中文对应：

```text
实时推理（RealTimeInference，RT）
批量推理（BatchInference）
AI训练（AITraining）
```

之后保持一种写法，不在 `RT / RealTimeInference / 实时任务` 三种称呼之间来回切换。

## 4. 模型汇总必须像数学模型

“模型汇总”应直接给完整数学结构，不写“目标函数直接写为”“物业函数”“使用某函数可表示为”等口语句。

推荐：

```text
综合上述定义，模型为
[min / max / lex min]
subject to
[核心约束]
```

或者直接给 `lex min / min / max + s.t.`。模型汇总的目的，是让读者不回翻正文也能看清决策变量、目标和约束。

## 5. 算法介绍不能只有一大段文字

算法小节至少包含三层信息：

1. 为什么该算法适合当前数学结构；
2. 1--2 个真正决定搜索/更新规则的数学量，例如排序键、约化成本、接受准则；
3. 伪代码。

不要先写半页自然语言，再放一张伪代码。

伪代码以中文描述动作，但保留正式控制结构。推荐“输入 / 初始化 / 输出”为中文，`for / if / while` 可保留统一的算法关键字；不要整段全英文，也不要把 Python 代码逐行翻译成中文。

## 6. 图表必须被正文引用并解释

每张图、每张表至少完成两件事：

- 正文出现一次 `图\ref{...}` 或 `表\ref{...}`；
- 紧邻位置说明它回答了什么问题，而不是重复图题。

若图表与文字完全重复，优先删图表或压缩文字。若两个指标相差多个数量级、零值较多且需要保留单位和精确值，优先用表格而不是强行画同一坐标图。

默认尺寸：单图 `0.44\textwidth`；两个独立小图并排每个约 `0.44\textwidth`；Origin 已合成双面板整张 `0.88\textwidth`；总体流程图 `1.0\textwidth`；机理图一般 `0.70\textwidth`。

不要为了“填版面”机械放图。Q4 这类复杂联合模型优先保留“为什么需要联合 → 为什么顺序法有偏差 → 联合后改善什么”三类图。

## 7. 表格宽度不要用错误方法硬拉

彩色表头需要保持连续背景。若双列表过窄，优先局部增加 `\tabcolsep`；若多列表接近正文宽度，再使用 `tabular*` 或 `resizebox`。不要把原本正常的多列表为了拉宽另一个表而全局改成 `tabular*`。

符号表使用 `tabularx` 时可局部增加：

```tex
\setlength{\extrarowheight}{2pt}
```

避免符号说明过挤。

## 8. 浮动体与分页

`[H]` 流程图后若紧跟“标题 + 长段落 + 多行 align”，LaTeX 可能把整块推到下一页并留下大空白。遇到这种情况优先：

- 拆分连续 `align`；
- 把可独立的公式改成多个 `equation`；
- 缩短紧随图片的大段文字。

不要首先缩小已经合适的流程图，也不要随意删除 `FloatBarrier`。

## 9. 摘要终稿

摘要首页优先保证一页内完成。排版基线：标题到“摘要”较紧，“摘要”到正文略大，各问之间有小段距。

加粗只用于：

- 核心模型/算法名称；
- 最关键结果数字或结论词。

不要整句、整段加粗。场景分析直接回答“什么因素影响什么指标”，不要写“对应同一可行域”“约束退化”等内部推导结论作为摘要主句。

## 10. 参考文献与代码附录

15 条左右参考文献可用 `\footnotesize` 和较小条目间距争取一页排完，但不通过压缩到难以阅读的字号实现。

代码附录按比赛提交规则二选一：

- 另交源码：正文列文件与功能，附少量核心片段；
- 只交 PDF 且代码页不计正文页数：用 `\lstinputlisting` 直接收入各问最终核心程序，避免手工复制导致版本不一致。

## 11. 全文临时集成

章节责任分支之间长期并行开发时，不再用临时 `git merge` 把所有 feature 分支硬合到一个 worktree。预览采用“责任域审计 + 文件 overlay”：

```text
feature/paper-shell 作为排版底座
→ 按责任域从各 feature 分支覆盖其 canonical 文件
→ 检查跨域修改
→ 检查冲突标记/资源路径/引用/结果状态
→ 编译临时 PDF
```

推荐从稳定仓库根目录运行：

```bash
git fetch origin --prune
bash <(git show origin/feature/shared:scripts/preview_latest.sh)
```

脚本会自动清理上次失败遗留的临时 worktree，并始终使用远端最新的 preview 代码。

## 12. 终稿人工检查顺序

1. 先看标题与摘要：标题是否同时体现问题和代表性模型/算法，摘要是否只保留关键加粗；
2. 再看问题描述、预备工作：有没有大段散文和内部表述；
3. 再看模型汇总：是否能独立读懂目标和约束；
4. 再看算法：是否有核心数学量，而不是只有文字；
5. 逐图逐表检查“正文引用 + 解释”；
6. 检查模型/算法首次出现是否为“中文 + 英文全称 + 缩写”；
7. 检查英文是否来自附件字段或必要专业名词；
8. 检查“严格、口径、证据边界、层级、链路”等词是否真有必要；
9. 检查跨问比较是否使用同一时间范围、终端结算和单位；
10. 抽查正文参数是否与正式代码一致；
11. 最后运行 preview 与 `final_preflight.py`，再人工看分页、表头、图宽和参考文献。

## 13. 标题不是摘要缩写

标题优先体现“研究问题 + 代表性模型 + 代表性求解算法”，先完整再压缩；若信息过多可使用副标题。避免：

- 只有“某某优化”“某某协同”而没有模型信息；
- 把四问内部缩写全部堆进标题；
- 使用“研究”“机制”“框架”等不能增加辨识度的空词；
- 为省字直接使用评委不一定认识的自定义缩写。

若题目主线跨多问，应选真正贯穿全文的模型类别，不要只用最后一问算法代替全文标题。

## 14. 场景结果与最优性证书分开写

场景分析中必须区分：

- 已获得优化证书的结果；
- 与基准等价的场景；
- 只有上下界的有界结果；
- 仅通过硬约束检查的可行候选。

可行候选的迁移率、等待、碳排等只能称“候选方案指标”，不能写成该场景“最优策略”。若成本层尚有明显 Gap，应把上下界和 Gap 一并给出。

## 15. 跨问题比较前统一计算范围

跨问比较绝对成本、碳排或储能收益前，至少核对：

```text
时间范围
终端小时是否计费
SOC 初末约束
购售电定义
任务完成边界
单位与基准方案
```

若这些条件尚未统一，不要把绝对差解释成“联合优化新增收益”；优先报告同一问题内部的相对变化。

## 16. 代码、正文和 canonical 文件一致

终稿前抽查蒙特卡洛次数、容差、迭代次数、场景幅度、时间范围等关键参数是否与正式代码一致。发现不一致时先确认哪一端是已验证真源，不为迁就旧文案随意改代码。

`modules/*/paper/` 不保留 `_final`、`_v2`、`_old`、`_backup` 等平行正文。参考文献只维护 `references.tex`，旧稿统一归档到 `work/archive/`。
